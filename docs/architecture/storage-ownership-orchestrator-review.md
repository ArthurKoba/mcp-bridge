## 3. Source FK and transaction boundary conversion

Of the 42 SQLAlchemy cross-schema FKs, candidate owner groupings preserve just four internal owner relationships: two Control→Control, one Catalog→Catalog and one Access→Access; other **38** become cross-owner opaque ID/reference checks with NO PostgreSQL FK. Verified concentration by source→target owner: Catalog→Control (6); Access→Identity (4); Access→Control (3); Files→Control (3); Control→Identity (3); Catalog→Identity (2); Catalog→Access (2); Reverse→Files (2); Reverse→Control (2); Runtime→Identity (2); Runtime→Control (2); Runtime→Access (2); plus lower-count edges. See full 42-row source inventory in D4 package; agents must prove the target grouping does not violate any foreign-key, ownership, deletion/retention or grant rule.

**Immutable owner-local transactions:** within a domain database, record authoritative state + owner-scoped command deduplication + owner-local audit/outbox atomically. Cross-owner side effects are authenticated versioned API commands and idempotent event consumers, **not** `Session.begin()` spanning databases, SQL joins or shared FKs. Do not place all command status, outbox, browser telemetry or native receipts back in Authorization as a shortcut.

- **Identity → Access:** Identity is authoritative for current User activity, bootstrap/first-superuser and token revocation. Auth MAY cache a bounded signed user proof for low-risk presentation, but an elevated/sensitive effect must use current verified Identity status and revoke epoch or deny when owner unavailable. Identity must not rely on Team/Project SQL FK before deactivation; hard deletion is denied until Control reports no ownership and a versioned, fenced transfer/hold completes. Last-superuser invariant is Identity-local.
- **Control → Access:** Team membership, Team owner, Project owner and Agent identity are authoritative in Control. Access grants/AgentSession remain separate; approval/use/revoke checks compare current Control authorization revision with Auth grant/session version at the effect boundary. Membership/owner change invalidates derived capability using a fenced revocation epoch; if Control/Identity cannot be checked, elevated/provider/file/process operations **DENY**, not stale allow. Control owns Team/Project transfer atomicity locally. Access cannot mutate Control members or Project ownership via its DB.
- **Control/Access → Catalog/Files/Runtime/Reverse:** an owner may store opaque `UserId`/`TeamId`/`ProjectId`/`AgentSessionId` but cannot issue authority from mere UUID possession. Require signed short-lived recipient-bound, action-scoped authorization and source-owner version checks at effect time. Resource credential custody cannot be moved into Gateway/Terminal env; File/runtime unknown external effects need original operation UUID + signed inspect/reconcile and no speculative retry.
- **Delete, move and saga:** a Project transfer/revoke and an integration/Files/native lifecycle cannot be declared atomic across databases. Stage versioned desired state in Control, propagate via owner-local outbox and signed idempotent commands, compare revision before granting use, and compensate/resume on unknown outcomes. A removed/disabled User or Team member loses privilege before asynchronous projection catches up. Each owner has a declared retention/fencing strategy and observable `pending/unknown/reconciled` status, not an implicit distributed rollback.
- **Event aggregation:** Control-owned `scope_events/cursors/receipts` may be a user-facing read projection only, backed by owner-local outboxes and scope-filtered event versions. Never treat a remote WS event or eventual projection as an authorization check. Bulk `MCP calls`, tool traces and diagnostic events go to OTLP/SigNoz or a separately approved high-ingest owner, not a universal Authorization `audit` table.

## 4. Deployment, privileges, migrations, readiness

- **Physical provisioning:** D owns the managed physical PostgreSQL service plus creation of new logical DBs/least-privileged roles/backups through an approved, reproducible infrastructure mechanism; provider availability, grants and secret scopes are to be investigated **read-only first**. No invented Coolify API endpoint or credential, no manually executed ad hoc SQL and no duplicate Application secrets. Current `External Services` volumes, data identity, network and live app remain untouched until bounded owner authorization.
- **Per-owner migrations:** each persistent owner (Identity, Access, Platform, Catalog, and Files/Runtime/Reverse when activated) owns its ONLY source-tracked Alembic graph, migration lock/version fence and rollout ordering in its normal trusted startup. Auth MUST cease importing/migrating other owners' ORM or `platform_metadata()`; the published global `0001/0002` is a **superseded artifact** and CANNOT be stamped onto a new per-owner DB. No separate global migrator/Core service, generic migration ENV switch, manual schema-init job, `create_all`, or unsafe auto-downgrade. D approves required migration role vs runtime role privileges, bounded wait/lock, non-destructive forward-only change plans, backups, upgrade compatibility and rollback at every owner gate.
- **Topology:** separate logical DBs may share physical Postgres and `briareus-net` initially, but distinct DB roles and application-specific authentication/SQL grants enforce least privilege. A shared Docker network is NOT a trust perimeter. Additional private networks / separate Postgres only with verified DNS/Coolify reachability and measurable isolation justification; no blanket per-module network duplication or accidental loss of service discovery.
- **Readiness:** Data postgres/Valkey health is not a platform schema readiness promise. The responsible owner's ready state means its OWN expected revision/role and authenticated dependency contract verified. Gateway/Admin UI/BFF must not claim working login or tools while Identity/Access/Control unavailable. Protected C1-B2/C2 remains unmounted/fail-closed until peer TLS/Unix, current User, Team/Project, AgentSession grant, native OS and revocation are independently accepted.
